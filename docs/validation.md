# 验证记录与边界

### 原系统已有的验证

项目作者已在不同局域网间完成以下链路：电脑浏览器通过 HTTPS 进入阿里云 ECS 承载的云平台，云平台经 frps 回环 TCP 代理、板端主动建立的 FRP/TLS 工作连接，访问 GD32H757VMT6 的本机 Web 服务并取得响应。这是本项目要展示的工程成果。

### 如何复现跨局域网验证

先确认 [板端最低前提](firmware.md) 和 [服务器最低前提](deployment.md) 均已满足。建议分两阶段验收：先打通板端与服务器回环转发，再增加电脑浏览器与 HTTPS 入口。

| 阶段 | 验收证据 | 常见阻碍 |
| --- | --- | --- |
| 本机服务 | 板端任务能访问 `127.0.0.1:8080` | Web 未启动、监听地址不接收回环、lwIP 回环未开启 |
| 认证引导 | 板端获得通过 HMAC 校验的 UTC 和代理端口 | UDP 7000 未放行、设备 ID/密钥不匹配、引导服务未运行、服务器时钟错误 |
| TLS/FRP | 证书验证成功、FRP 登录及代理注册成功 | IP SAN/CA 错误、token 不匹配、服务端版本不是 0.71.1、tcpMux 未关闭 |
| 最小转发 | ECS 中 `curl --fail --max-time 15 http://127.0.0.1:18080/` 返回板端实际响应 | 代理端口未注册、本机服务不可达、工作连接资源不足 |
| 浏览器跨 LAN | 另一局域网浏览器经 HTTPS/入口认证取得板端实际页面或数据 | TCP 443、安全组、域名/浏览器证书、Nginx 上游配置错误 |

`systemctl` 显示服务 active、能打开云端登录页或板端启动函数返回 true，都不能单独替代最小转发或浏览器验收。默认日志关闭，需要先把 `CLOUD_LOG` 接入自己的线程安全日志，才可观察下列串口状态。

1. 在板端 LAN B 先确认本机 Web 可用、网关正确；在 LAN A 准备电脑浏览器。记录两个网络使用不同出口，记录留在自己的私有验收资料中。
2. 按部署文档运行自己的 ECS/frps、认证引导和 HTTPS 入口。检查固件版本响应、证书/IP SAN 与凭据一致。
3. 通过串口日志确认认证对时成功、TLS 建连、FRP 登录及代理在线；在 ECS 用 `curl --fail http://127.0.0.1:18080/` 检查板端响应。
4. 在 LAN A 浏览器访问自己的 HTTPS 域名并登录，验证返回的是板端实际页面/只读数据；不要仅以云端登录页可打开作为板端贯通证据。
5. 如需验证恢复，单独安排板端断网/恢复并记录重连及本地服务状态；不要对运行中的业务设备随意做破坏性测试。

主机复核命令：

```sh
python -m unittest discover -s tests -v
python tests/run_interop.py --cc gcc --mbedtls /path/to/mbedtls-3.6.7
python tools/check_public.py
```

性能、长期稳定性、设备容量、并发吞吐、完整官方 frpc 功能兼容和生产安全性均不从这组连接测试推导。
